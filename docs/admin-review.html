Admin System — Review & Plan

Haflati · Laravel 12 API · review of the admin module added by Amer · 2026-06-06

Executive summary

The admin module is a solid foundation and the right overall path: a dedicated auth:admins Sanctum guard, hashed passwords, token abilities, and role middleware. The main weakness is the role split: the support admin is currently locked out of almost everything (super_admin-only), which is too blunt. Below is the recommended permission model plus a prioritized fix list.

1. Architecture — Good path, keep it

Strengths found in the actual code:

  • Separate admins guard in config/auth.php — admins are isolated from users/vendors. Correct.
  • Password hashing via Hash::check + 'password' => 'hashed' cast on the Admin model.
  • Token ability scoping on login (AdminAuthController.php:29).
  • Sensitive fields hidden on the model (Admin.php:20).
  • Login returns a generic error so you can't tell if an email exists (anti-enumeration).
  • Bookings/payments lists eager-load relations (no obvious N+1 there).

2. Role split — Too blunt, needs rework

Root cause: EnsureAdminRole does an exact match ($admin->role !== $role, EnsureAdminRole.php:14) and is only ever applied as role:super_admin (routes/api.php). Result: support gets 403 on the whole dashboard / users / vendors / bookings / payments group — they can't even open the dashboard.

Two fixes are needed: (a) make the middleware accept a list of roles (e.g. role:super_admin,support), and (b) split routes into "view" (both roles) vs "act/sensitive" (super_admin only).

3. The open question — should support see the dashboard?

Recommendation: YES. Let support see the dashboard and the lists (read-only), but deny banning users/vendors and anything touching payments. This matches your instinct and follows two standard rules: least privilege (only the access needed for the job) and separation of duties (the person handling complaints shouldn't also control money or bans).

How to implement it (route restructure)

  • Group 1 — auth:admins + role:super_admin,support: dashboard, list users/vendors/bookings, KYC approve/reject.
  • Group 2 — auth:admins + role:super_admin: ban user, toggle vendor, payments/refunds, reports, manage admins.
  • Change EnsureAdminRole to split the param on commas and check in_array($admin->role, $roles).

4. Bugs & security findings

HIGHReject vendor leaks the "ban" power. rejectVendor (AdminController.php:59-67) validates reason but never stores/uses it, and it sets is_active=false. Since reject is allowed for support, support can effectively disable any vendor — the exact power you want restricted. Fix: store the reason, and make "disable/ban" a separate super_admin-only action distinct from KYC reject.

5. What's missing — prioritized

  • P1 Rate-limit /admin/login (none today, routes/api.php) — protect against brute force with throttle.
  • P1 Fix the role split (matrix above).
  • P2 Pagination on every admin list.
  • P2 Audit log — record every admin action (who, what, when). Critical for a money platform.
  • P3 Admin seeder (none exists — there's no way to create the first admin yet).
  • P3 last_login_at tracking, complaint-handling endpoints, admin password reset.
  • P3 Soft-deletes on users/vendors instead of hard delete; trim list payloads to needed fields.
