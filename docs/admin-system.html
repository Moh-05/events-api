Admin System — Full Reference

Haflati · حفلتي — API + behaviour reference for the admin panel (for the React frontend design). All routes are prefixed with /api.

Two roles, two layers of auth

Every admin route sits behind auth:admins (a dedicated Sanctum guard). Sensitive routes add a role: layer. Login is throttled to 5 tries/min.

super_admin full control — bans, money, disputes, moderation, managing admins.
super_admin + support view + KYC only. Support never touches money, bans, or content deletion.

Revokes the current access token.

3 · Dashboard & statistics

GET
/admin/dashboard both
Headline overview: total_users, vendors (total / approved / pending / banned), bookings (total / active / completed), and profit (profit_today / profit_month / profit_all_time).
GET
/admin/stats/financial super_admin
Full money report. summary (all-time gross_volume, platform_profit, vendor_payouts, transactions) + today / this_month / this_year windows + monthly_trend (last 12 months, zero-filled → ready for a chart).

Money vocabulary

gross_volume — what customers paid.
platform_profit — the commission (your cut).
vendor_payouts — what vendors earned.

Chart-ready

monthly_trend is an array of 12 {month, gross_volume, platform_profit, transactions}, oldest→newest, gaps filled with 0. Feed straight into a bar/line chart.

4 · Vendors

GET
/admin/vendors both
Paginated list. ?search= (name/business/phone)   ?is_active=0|1
GET
/admin/vendors/pending both
KYC queue — vendors awaiting approval (is_approved=false).
GET
/admin/vendors/{id} both
One vendor + their products. Includes account_status (see §9).
POST
/admin/vendors/{id}/approve both
Approve KYC → is_approved=true, clears any rejection reason.
POST
/admin/vendors/{id}/reject both
Reject KYC with a required reason. Stored on the vendor. Does NOT ban an active vendor — that's separate.
POST
/admin/vendors/{id}/ban super_admin
Immediate ban. Cancels + refunds ALL in-flight bookings, then fully bans. Optional reason. → account_status: banned. Use for fraud / urgent.
POST
/admin/vendors/{id}/ban-gradual super_admin
Ban after winding down. Refunds pending bookings, keeps approved ones so the vendor can finish, then auto-bans when the last one is done. → account_status: winding_down.
POST
/admin/vendors/{id}/unban super_admin
Reinstate a banned / winding-down vendor → account_status: active.
GET
/admin/vendors/{id}/wallet super_admin
A vendor's wallet: available_balance, pending_clearance, total_earned + full ledger. For money disputes.

10 · Key concepts (behaviour)

Vendor account states

active is_active=1 → normal, visible, takes bookings winding_down is_active=0, winding_down=1 → hidden + no new bookings, but can log in to FINISH existing approved bookings banned is_active=0, winding_down=0 → fully blocked

The API exposes a computed account_status = active | winding_down | banned on every vendor object — use it directly for status badges/filters in the UI.

Two ban modes

Immediate → cancel + refund ALL, ban now. (fraud) Gradual → refund pending, keep approved, auto-ban when done. (normal removal)

Escrow (why refunds are safe)

A vendor's earnings stay pending until the booking is completed (service delivered) — not withdrawable before. So if a booking is cancelled/banned before the event, the money is still held and the customer can always be refunded.

Refund fairness

Who cancelsCustomer gets back
Platform (admin ban / dispute)100% — customer did nothing wrong
Customer, within 24h of approval100%
Customer, 24–72h50%
Customer, after 72h0%

The amount owed is stored on the booking (refund_amount, refund_paid_at) so it shows up in /admin/refunds-due until paid.
