Admin System — Full Reference

Haflati · حفلتي — complete API + behaviour reference for the admin panel (React). All routes are prefixed with /api. Sections marked NEW were added in the Jul–Aug 2026 build.

Two roles, two layers of auth

Every admin route sits behind auth:admins (a dedicated Sanctum guard). Sensitive routes add a role: layer. Login is throttled to 5 tries/min.

super_admin full control — bans, all money, disputes, moderation deletion, managing admins.
super_admin + support everything viewing + KYC + handling support. Support never touches money, bans, content deletion, or dispute/cancel.

3 · Dashboard & statistics

GET
/admin/dashboard both
stats: total_users, vendors (total / approved / pending / banned), bookings (total / active / completed), profit (profit_today / profit_month / profit_all_time — gross). nav_badges NEW: live sidebar red-dot counts → pending_vendors, unread_support, reported_content, refunds_due, unpaid_withdrawals.
GET
/admin/stats/financial super_admin
Full money report. summary (all-time gross: gross_volume, platform_profit, vendor_payouts, transactions) · net NEW (honest bottom line — see §12) · today / this_month / this_year · monthly_trend (12 months, zero-filled, chart-ready).

Sidebar badges vs the bell

nav_badges = live counts ("how much work is pending, where"). The bell (§4) = an event feed ("what happened, when, click to open"). They complement each other — use badges for red dots, the bell for the dropdown.

Chart-ready

monthly_trend is an array of 12 {month, gross_volume, platform_profit, transactions}, oldest→newest, gaps filled with 0. Feed straight into a bar/line chart.

4 · Notifications — the bell NEW

An event feed: every relevant event drops a notification into the admin's inbox (its own read state per admin). Reuses the shared notifications table (notifiable_type=admin). Available to every admin.

GET
/admin/notifications any admin
This admin's feed (newest first) + unread_count. Each item: title, body, read_at, and data.type = vendor_kyc | support | content_report | withdrawal | refund_due + the target id → deep-link the click.
POST
/admin/notifications/read-all any admin
Mark all of this admin's notifications read.
POST
/admin/notifications/{id}/read any admin
Mark one read. 404 if it isn't this admin's notification.

Who gets what: KYC + support → both roles · content report / withdrawal / refund-due → super_admin only (targeted at whoever can act). Read state is per-admin.

5 · Vendors

GET
/admin/vendors both
Paginated list. ?search= (name/business/phone)   ?status=kyc_pending|active|winding_down|banned NEW (the four account-state tabs — a true partition)   ?is_active=0|1 (still works).
GET
/admin/vendors/pending both
KYC queue — vendors awaiting approval (is_approved=false & not banned).
GET
/admin/vendors/{id} both
One vendor + their products, plus bookings_count + reviews_count NEW and account_status (see §12). Wallet is separate ↓.
POST
/admin/vendors/{id}/approve both
Approve KYC → is_approved=true, clears any rejection reason.
POST
/admin/vendors/{id}/reject both
Reject KYC with a required reason. Does NOT ban an active vendor — banning is separate.
POST
/admin/vendors/{id}/ban super_admin
Immediate ban (fraud). Cancels + refunds ALL in-flight bookings; on approved ones it also claws the platform commission back from the vendor NEW (see §12). Optional reason. → account_status: banned. Response carries cancelled_bookings + commission_charged.
POST
/admin/vendors/{id}/ban-gradual super_admin
Ban after winding down. Refunds pending bookings (100%), keeps approved ones so the vendor can finish, auto-bans when the last one is done. No commission clawback. → account_status: winding_down.
POST
/admin/vendors/{id}/unban super_admin
Reinstate a banned / winding-down vendor → account_status: active.
GET
/admin/vendors/{id}/wallet super_admin
A vendor's wallet: available_balance (can be negative = owes the platform after a clawback), pending_clearance, total_earned + full ledger.

GET
/admin/users both
Paginated list + bookings_count per row NEW. ?search= (name / phone)   ?is_active=0|1 NEW (Active / Banned tabs).
GET
/admin/users/{id} both
One user + their bookings (with vendor & product).
POST
/admin/users/{id}/toggle super_admin
Ban / unban a user (flips is_active; a banned user can't use the app). Guarded NEW: refuses (422 + count) if the user has a paid active booking — settle it first. Unpaid-draft-only → succeeds with a warning. Bookings/money are never auto-cancelled here; a ban is a pure lock-out.

7 · Bookings & disputes

GET
/admin/bookings both
Paginated list. ?status= ?vendor_id= ?user_id= ?search= NEW (booking id / customer / vendor name).
GET
/admin/bookings/{id} both
Full booking: customer, vendor, product, and payment.
POST
/admin/bookings/{id}/cancel super_admin
Dispute resolution. Cancels ONE booking, refunds the customer 100%, reverses the vendor's credit — vendor account untouched, no commission clawback (fault unclear). reason required.
POST
/admin/bookings/{id}/cancel-vendor-request super_admin
NEW Vendor asked to back out. Only for an approved booking (422 otherwise). Customer refunded 100% and the platform commission is charged to the vendor's wallet (he caused it). Response: refund_amount + commission_charged.

8 · Support (tickets & chats) NEW

One inbox for both user tickets and vendor chats. A user opens a ticket; it stays a one-way ticket until an admin replies (the admin decides whether it becomes a conversation). A vendor has one persistent chat. Both roles handle support.

GET
/admin/support both
Inbox. ?owner_type=user|vendor ?status=open|in_review|resolved ?unread=1. Returns counts (per status + total unread) and each thread with owner_name, owner_phone, unread_count.
GET
/admin/support/{id} both
Full thread: all messages + owner + the linked booking context (vendor, product, payment) for user tickets. Opening it marks the owner's messages read.
POST
/admin/support/{id}/messages both
Admin reply (message). On a fresh user ticket this opens the chat → moves it to in_review, sets handled_by, and notifies the owner.
POST
/admin/support/{id}/resolve both
Close the thread (audited, owner notified). A user ticket stays closed (new problem = new ticket); a vendor chat quietly reopens if the vendor writes again.

Ticket category (user tickets): no_show | payment | behavior | other — routes the admin to the right action (money vs vendor behaviour). The app-side ticket/report endpoints are in §13.

10 · Money oversight

GET
/admin/payments super_admin
All incoming payments (with booking → user & vendor).
GET
/admin/refunds-due super_admin
Cancelled/declined bookings that still owe the customer money + total_due. Excludes paid AND waived. The "to-pay-out" worklist.
POST
/admin/refunds/{id}/mark-paid super_admin
After sending the money manually, mark it paid → drops off the list. (Refused if the refund was waived.)
POST
/admin/refunds/{id}/waive super_admin
NEW Officially keep the money (e.g. fraud) — reason required, audited. The third fate of a refund: paid / waived / still-pending.
GET
/admin/withdrawals super_admin
Vendor withdrawal requests + total_unpaid. ?unpaid=1 = outstanding only (excludes paid AND rejected).
POST
/admin/withdrawals/{id}/mark-paid super_admin
Mark a vendor payout as sent. (Refused if the request was rejected.)
POST
/admin/withdrawals/{id}/reject super_admin
NEW Reject a suspicious request — reason required. The held amount returns to the vendor's available balance automatically, and it leaves the payout queue.

⚠️ The actual money send is manual for now — real automated payout waits on the ShamCash payout API. These endpoints give full visibility + tracking today.

12 · Key concepts (behaviour)

Vendor account states

active is_active=1 → normal, visible, takes bookings winding_down is_active=0, winding_down=1 → hidden + no new bookings, but can log in to FINISH existing approved bookings banned is_active=0, winding_down=0 → fully blocked

Every vendor object exposes a computed account_status = active | winding_down | banned — use it directly for badges/filters (or the ?status= filter on the list).

Two ban modes

Immediate → cancel + refund ALL; claw commission on approved ones. (fraud) Gradual → refund pending, keep approved, auto-ban when done. (normal removal)

Escrow (why refunds are safe)

A vendor's earnings stay pending until the booking is completed — not withdrawable before. So if a booking is cancelled/banned before the event, the money is still held and the customer can always be refunded.

Commission — who bears it on a cancellation NEW

A refund returns 100% to the customer. The question is who eats the platform's 15% commission:

CancellationCommission
Vendor-requested cancel · Fraud ban (approved bookings)charged to the vendor (he caused it) — wallet can go negative
Dispute cancel · Gradual banabsorbed by the platform (fault unclear / considerate removal)

Gross vs net profit NEW

stats/financial → net: gross_profit − commission_lost (refunds the platform absorbed) = net_profit. Also refunded_to_customers and commission_reclaimed (clawed back from vendors). The summary block stays gross; net is the honest bottom line.

Refund — three fates

Stored on the booking: refund_amount, refund_paid_at, refund_waived_at.
Paid (sent) · Waived (kept, e.g. fraud) · Pending (still in refunds-due).

Support model

User → ticket; can't reply until an admin does. Vendor → one persistent chat. Resolving closes a ticket for good; a vendor chat reopens on a new message.

Customer self-cancel — refund tiers

Who cancelsCustomer gets back
Platform (ban / dispute / vendor-request)100% — customer did nothing wrong
Customer, within 24h of approval100%
Customer, 24–72h50%
Customer, after 72h0%

13 · App-side endpoints that feed the admin NEW

These live on the customer / vendor apps (guards auth:sanctum / auth:vendors), not the admin panel — but they create the tickets, reports and requests the admin sees. Listed so the contract is complete.

POST
/support/tickets user
Open a ticket: subject, message, optional booking_id (own) + category. Also: GET /support/tickets, GET /support/tickets/{id}, POST /support/tickets/{id}/messages (only after an admin replied).
GET
/vendor/support vendor
The vendor's persistent support chat (auto-created). Send with POST /vendor/support/messages.
POST
/reviews/{id}/report · /products/{id}/report · /portfolio/{id}/report user
Report content (optional reason) → creates a pending report (the moderation badge). Vendors can report an abusive review via /vendor/reviews/{id}/report. Re-reporting is a silent no-op.
POST
/vendor/withdraw vendor
Vendor requests a payout of the full available balance → appears in /admin/withdrawals and pings super_admins.
